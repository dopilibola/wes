Alert escalation: EDA notes

Hackathon task: predict which monitoring alerts get escalated. Metric: ROC-AUC.

1. Approach

We have one row per alert and a long transaction log behind each one, so most of the work was turning that log into features. For every transaction we calculated how many days before the alert date it happened, and built all the windows (last day, last week, last month and so on) from that.

We ended up with 284 features per alert. We trained LightGBM with pretty heavy regularization and a logistic regression on quantile-transformed features, then averaged their ranks (60/40). Validation is 5-fold stratified CV repeated with 3 seeds. Out-of-fold AUC is .

2. Data

Some things we checked early on:

  • Each alert has about 180 days of history. A few transactions fall on the alert date itself.
  • Train and test alerts cover the same period (Jan 2025 – Dec 2026), so a random split is fine for validation.
  • We looked for the same transaction under two different alerts (same customer) and found none, so there's no customer linkage to use.
  • miqdor_indeksi looks like a standardized log amount. Incoming bank transfers have a floor at −2.912, and each type has its own maximum.
  • About 75% of transactions are incoming. Card is 54%, bank transfer 39%, cash 6%, international under 1%.

3. Target

17.2% of training alerts were escalated. The rate barely moves over time (16–19% per quarter), so the alert date on its own doesn't help much.

Escalation rate by quarter

4. Activity over time

Activity goes down as the alert gets closer: about 3 transactions a day around four months before, and about 1 a day in the last few weeks. The drop at day 179 is only the edge of the 180-day window. The day before the alert is very different: about 40 transactions, nearly all in the last hour (23:00–23:59). We think this burst is what fires the alert. But it looks the same for escalated and dismissed alerts, so it doesn't help separate them.

Escalated customers are a little more active overall (about 6% more transactions), and they have more transactions on the alert date itself.

5. Transaction amounts

This was the most useful finding. Escalated customers have smaller amounts: the mean miqdor_indeksi is 0.05–0.09 lower in every window. It shows up most in bank transfers, where small transfers are up to 15% more common and large ones about 30% less common for escalated alerts. Card payments show the same thing, but weaker. Cash shows almost no difference.

6. Transaction types and direction

We expected cash or international transfers to matter, but the type mix is almost identical between the two groups (within 0.2 percentage points), and so is the incoming/outgoing split. The difference is in the amounts inside each type, so we built amount features for each type and direction separately.

7. Features and model

Feature groups we kept:

  • Amount quantiles per type and direction (5/25/50/75/95%, std, skew). These came straight from section 5 and moved CV AUC from 0.638 to 0.646.
  • Window features for 1, 3, 7, 14, 30, 60, 90 and 180 days: counts, amount mean/max/std, outgoing share, counts per type.
  • Recent vs. earlier: activity and amounts in the last 1–30 days compared with the rest of the history.
  • Timing: gaps between transactions, busiest day, monthly trend, night and weekend share.

What we tried and dropped, because CV didn't improve: hour and weekday histograms, features about the last-day burst, in-then-out transfer pairs, CatBoost, and a transaction-level model (AUC 0.556).

8. Further analysis after the first model

After the first submission we kept looking for signal the model might be missing. We compared every idea against the same baseline, 5-fold CV repeated with 5 seeds (0.6470 ± 0.0012), so small gains could be told apart from noise.

Three new patterns showed up in the data:

  • The −2.912 floor. 14% of alerts have at least one incoming bank transfer at the minimum amount index. Only 9.8% of those alerts were escalated, compared with 18.4% of the rest.
  • Weekly rhythm. We measured how similar a customer's daily transaction counts are one week apart (lag-7 autocorrelation). Escalated customers are a bit more regular week to week, and the escalation rate rises from 15.1% to 19.2% across quintiles.
  • Steadier amounts. The average jump between one transaction's amount and the next is smaller for escalated customers. The escalation rate falls from 20.5% to 13.7% across quintiles.

These patterns are real, but they overlap with features the model already had. For example, the floor effect is mostly covered by the bank-transfer amount quantiles. None of the experiments below cleared the +0.005 bar we set before resubmitting, so we kept the original model.

We also checked structure outside the transactions: alert ID and file order, how many alerts arrive on the same day, and escalation rate by date, week and month. All of it looked like random noise (AUC 0.49–0.51).

9. Conclusion

  1. All alerts come after a similar late-night burst of transactions, so the burst alone doesn't tell you much. The customer's earlier history matters more.
  2. Transaction size is the main signal. Escalated customers have smaller bank transfers and card payments over the whole 180 days.
  3. They are slightly more active, but their type mix is the same as everyone else's.
  4. No single feature gets above ~0.575 AUC. Combining them gets to 0.649, and 30+ further experiments stayed within 0.646–0.6485, which looks like the ceiling for this data. Logistic regression is close to LightGBM, which suggests the signal is mostly simple and monotonic.
